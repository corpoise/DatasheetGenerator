# ProjectCommonRule

## 응답 어조

모든 응답은 공손하고 격식 있는 존댓말로 작성한다.
답변은 최대한 간결하게 작성하되, 중요한 내용·이슈·실패 원인·조치 내용은 사용자가 판단할 수 있을 만큼 상세하게 작성한다.

## 프로젝트 작성 지침

1. 사용자가 명시적으로 요청하지 않은 기능, 버튼, UI 요소, 메서드는 추가하지 않는다.

2. 실제 코드를 추가/수정/삭제하는 작업을 시작하기 전, 현재 모델이 Sonnet이 아닌 경우 사용자에게 현재 모델로 진행할지 승인을 받은 후 진행한다.

3. 신규 솔루션 또는 프로젝트를 처음 생성할 때, 작업을 시작하기 전에 사용자에게 솔루션명과 프로젝트명을 먼저 물어본다.

4. 사용자에게 코드를 제공하기 전에 반드시 아래 순서를 따른다:
   - `.editorconfig` 파일이 없으면 프로젝트 코딩 규칙에 맞게 생성한다.
   - `dotnet build` 로 빌드 성공 여부를 확인한다.
   - `dotnet format --verify-no-changes` 로 정적 검사를 수행한다.
   - 오류나 경고가 있으면 수정 후 위 과정을 다시 반복한다.
   - 모든 검사를 통과한 경우에만 사용자에게 결과물을 제공한다.

5. 결과물은 발생할 수 있는 이슈, 버그, 예외가 최대한 제거된 상태로 작성한다. 이를 위해 기능적 변경이나 작업 방향 변경이 필요한 경우, 사용자에게 변경 필요성과 영향을 설명한 뒤 처리 여부를 물어보고 사용자의 판단에 따라 진행한다.

6. 컨벤션 또는 규칙 문서에 새로운 규칙을 추가하거나 기존 규칙을 변경 또는 삭제해야 하는 경우, 변경 전에 반드시 사용자에게 변경 대상과 변경 내용을 설명하고 승인을 받는다.
   - 사용자의 명시적 승인 없이 규칙을 추가, 변경, 삭제하지 않는다.
   - 승인받은 범위 안에서만 규칙 문서를 수정한다.
   - 승인 후 수정한 규칙이 현재 작업 중인 대상 프로젝트에 영향을 주는지 확인한다.

7. 컨벤션에 새로운 규칙이 추가되거나 기존 규칙이 수정되는 경우, 현재 작업 중인 대상 프로젝트에 변경된 컨벤션을 다시 적용한다.
   - 변경된 규칙에 영향을 받는 코드 후보를 먼저 검색한다.
   - 수정 대상과 수정 방향을 사용자에게 설명하고 승인받는다.
   - 승인 후 코드를 수정한다.
   - `dotnet build` 로 빌드 성공 여부를 확인한다.
   - `dotnet format --verify-no-changes` 로 정적 검사를 수행한다.
   - 오류나 경고가 있으면 수정 후 위 과정을 다시 반복한다.

8. json, schema, excel 파일을 직접 수정하는 작업을 진행할 시, 작업 대상 파일의 사본을 먼저 생성한 후 작업을 진행한다. 작업이 완료되면 사본을 제거한다.

## 테스트 작성 원칙

코드 추가/수정/삭제 또는 컨벤션 재적용으로 동작이 바뀌는 경우, 구현 전에 변경 대상의 기대 동작과 실패 케이스를 테스트로 먼저 정의한다.

1. 테스트 코드는 대상 프로젝트 내부에 작성하지 않고, 별도의 테스트 전용 프로젝트를 생성하거나 기존 테스트 프로젝트를 사용한다.
   - 테스트 프로젝트는 대상 프로젝트와 1:1로 대응되어야 한다.
   - 하나의 테스트 프로젝트가 여러 대상 프로젝트를 동시에 테스트하지 않는다.
   - 하나의 대상 프로젝트에 여러 테스트 프로젝트를 만들지 않는다.
   - 테스트 프로젝트는 대상 프로젝트를 `ProjectReference`로 참조한다.
   - 테스트 프로젝트명은 대상 프로젝트명 뒤에 `.Tests`를 붙인다.
   - 예: `DatasheetGenerator` → `DatasheetGenerator.Tests`

2. 동일한 대상 타입에 대한 모든 테스트 코드는 하나의 테스트 파일에 작성한다.
   - 테스트 파일명은 대상 타입명 뒤에 `Tests.cs`를 붙인다.
   - 예: `DatasheetExporter` → `DatasheetExporterTests.cs`
   - 같은 대상 타입의 테스트를 여러 파일로 분리하지 않는다.
   - 파일 내부에서는 기능별 영역 또는 중첩 클래스로 테스트를 구분한다.

3. 테스트를 작성하기 위해 제품 로직을 변경해서는 안 된다.
   - 테스트 편의를 위해 실제 동작, 검증 조건, 예외 처리, 접근 제한자, 상태 변경 흐름을 바꾸지 않는다.
   - 테스트가 어렵다면 제품 로직을 왜곡하지 말고, 테스트 가능한 경계(Service, Validator, Parser 등)를 분리하는 방향을 먼저 검토한다.
   - 불가피하게 구조 변경이 필요한 경우, 변경 이유와 동작 영향이 없음을 사용자에게 설명하고 승인받는다.

4. 도메인 로직, 검증, 변환, 파싱, Export/Import, 파일 처리 로직은 단위 테스트 또는 통합 테스트를 작성한다.

5. 버그 수정은 수정 전에 실패하는 회귀 테스트를 먼저 작성한다.

6. 파일 I/O 테스트는 임시 디렉토리를 사용하며, 사용자 실제 경로나 고정 경로에 의존하지 않는다.

7. WPF, WinUI, WinForms 등 UI 프로젝트인 경우에만 UI 관련 테스트/QA 규칙을 적용한다.
   - UI 이벤트에 핵심 로직을 직접 두지 않고 ViewModel 또는 Service로 분리하여 테스트한다.
   - ViewModel 또는 Service는 테스트 프로젝트에서 단위 테스트한다.
   - XAML 레이아웃, 파일 다이얼로그, OS 종속 UI 동작처럼 자동 테스트가 과도하게 어렵거나 불안정한 경우, 자동 테스트 제외 사유와 수동 QA 체크리스트를 작성하고 사용자에게 보고한다.

8. UI 프로젝트가 아닌 경우에는 UI 테스트/수동 UI QA 규칙을 적용하지 않는다.

9. 테스트 작성 후 구현하고, 구현 후 `dotnet build`, 테스트 실행, `dotnet format --verify-no-changes`를 수행한다.

10. 작업 완료 전 변경 결과에 대한 자체 리뷰를 수행하고 결과를 사용자에게 보고한다.
   - 변경된 코드에 `CodeStyle.md`의 규칙이 모두 적용되어 있는지 확인한다.
   - 작업 절차에 `ProjectCommonRule.md`의 규칙이 모두 적용되어 있는지 확인한다.
   - 작업 판단과 변경 범위가 `Doctrine.md`의 원칙에 맞게 진행되었는지 확인한다.
   - 문제점
   - 우려점
   - 더 좋은 방향
   - 남은 리스크

## 완료 보고 형식

코드 추가/수정/삭제 또는 컨벤션 재적용 작업을 완료할 때는 아래 항목을 사용자에게 보고한다.

완료 보고는 불필요한 표현 없이 단락형으로 작성한다. 단, 중요한 내용, 이슈, 버그, 실패 원인, 조치 내용, 남은 리스크는 사용자가 판단할 수 있을 만큼 상세하게 작성한다.

- 변경 요약
- 테스트
- 빌드/포맷 검증
- QA 결과

현재 프로젝트 적용 결과, 테스트, 빌드/포맷 검증은 이슈가 없으면 `성공`으로만 보고한다. 이슈가 있는 경우에만 실패 항목, 원인, 조치 내용을 상세히 작성한다.
- 자체 리뷰
  - `CodeStyle.md` 적용 여부
  - `ProjectCommonRule.md` 적용 여부
  - `Doctrine.md` 준수 여부
  - 문제점
  - 우려점
  - 더 좋은 방향
  - 남은 리스크

## 오타 확인 규칙

사용자 요청, 파일명, 채널명, 경로, ID, 명령어, 클래스명, 메서드명, 설정값 등에서 오타로 의심되는 내용을 발견하면 임의로 고치지 않는다.

오타로 의심되는 경우 먼저 사용자에게 “오타인 듯한데, 이 값으로 수정해도 될까요?”처럼 확인 질문을 보낸다.

확인 질문에는 원문과 예상 수정안을 함께 제시한다.

사용자가 승인하거나 수정 의도를 명확히 답변한 뒤에만 해당 오타를 수정하고 작업을 진행한다.

사용자의 승인이 없으면 오타로 의심되는 값을 임의로 변경하지 않고 원문 기준으로 보류한다. 오타 가능성이 작업 대상 식별, 실행 명령, 파일 위치, 외부 연동 대상, 승인 대상, 또는 작업 결과에 영향을 줄 수 있으면 작업을 중단한다.

단순한 문맥상 오타처럼 보여도 파일명, 채널명, 경로, ID, 명령어, 식별자는 실제 값일 수 있으므로 확인 없이 변경하지 않는다.
